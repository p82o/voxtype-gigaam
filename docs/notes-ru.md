## Диагностика

### Зависание на границе 25 секунд

При длине аудио больше `25 * 16000` сэмплов сервер переходит к чанкам по
22 секунды. Обработчик запроса и обработка чанков захватывают один лок.
Прежний `threading.Lock` приводил к повторному захвату в том же потоке и
вечному ожиданию. Используется `threading.RLock`; регрессия проверяется
записью 25.003 секунды в `verify.sh`.

`/health` захватывает тот же лок, чтобы watchdog обнаруживал зависание inference.
Двойная проверка 15/5/15 секунд снижает вероятность перезапуска во время
распознавания. Первые 120 секунд после запуска выделены на загрузку модели.
При смене модели или оборудования сравните время inference с таймаутом watchdog.

### Пустая транскрипция

Синтетическая речь espeak иногда даёт пустой текст; для проверки используйте
официальный пример авторов через `./verify.sh --skip-watchdog`. Ожидается
русский текст с отрывком из «Евгения Онегина».
Если пуст и официальный пример, проверьте image ID, версии пакетов и совпадение
контрольных сумм модели. Transformers в текущем образе не используется.

### Длина записи

Установщик выставляет `audio.max_duration_secs = 300` и
`whisper.remote_timeout_secs = 60`. Первый параметр ограничивает запись,
второй — ожидание ответа ASR. После ручного изменения конфигурации перезапустите
voxtype. Для другого оборудования измерьте скорость inference перед изменением
таймаутов; приведённые выше времена относятся к проверенному компьютеру.

### Шум микрофона

Если OSD показывает сильную волну в тишине, проверьте ALSA capture и mic boost.
На исходной машине максимальные Capture и Boost давали около +60 дБ суммарно.
Практические ориентиры: шум в тишине RMS около 1% или меньше, пики речи 30–60%
без клиппинга. Нужный уровень зависит от микрофона и условий записи.

Измерение трёх секунд тишины через default source требует `parec`, `pactl`
и Python хоста только для этой диагностической команды:

```bash
timeout 3 parec -d "$(pactl get-default-source)" --rate=16000 --channels=1 --format=s16le \
 | python3 -c "import sys,struct,math; d=sys.stdin.buffer.read(); n=len(d)//2; v=struct.unpack('<%dh'%n,d[:n*2]); rms=(sum(x*x for x in v)/n)**0.5; print('peak %.1f%% rms %.2f%% (%.0f dBFS)'%(max(abs(x) for x in v)/327.68,rms/327.68,20*math.log10(max(rms,1)/32768)))"
```

Номер карты и имена контролов смотрите через `cat /proc/asound/cards` и
`amixer -c N scontents`. Настраивайте Capture и Mic Boost под свою карту;
значения прежнего компьютера не являются универсальными. Сохранение через
`pkexec alsactl store` требует прав администратора и выполняется агентом
только по явной просьбе пользователя.

### Текущее состояние

```bash
curl -sf -m 15 http://127.0.0.1:8394/health
docker inspect --format '{{.Image}} {{.State.Health.Status}}' gigaam-asr
systemctl --user is-active voxtype gigaam-watchdog.timer
systemctl --user list-timers gigaam-watchdog.timer
voxtype status
```

Логи ASR находятся в Docker, логи watchdog — в user journal. Перед отправкой
логов проверьте их содержимое; конфигурацию voxtype и распознанный текст
для диагностики публиковать не требуется.

## Проверка сценария новой установки

Восстановлен `config/voxtype-config.toml` как пример ASR-настроек; тест сверяет
его с результатом настоящего merger. Удалены обращения к прежнему venv-сервису
и поиск весов в старом каталоге GigaAM. Установщик проверяет наличие Buildx.

24 теста проходят, включая установку в пустые каталоги GigaAM, повторный запуск
без повторной загрузки, отказ до создания стека при ошибке аудита и при
повреждённой загрузке. В изолированной копии установщика пользовательские пути
перенаправлены в временный каталог; Docker, systemd и HTTP заменены заглушками.
Подготовка модели, SHA-256, проверка полноты аудита и merger выполняются настоящими
скриптами. Это проверка последовательности установки, а не развёртывание на
другом компьютере.

Отдельно проверена настоящая загрузка архива официального GigaAM и обоих файлов
модели в пустой временный каталог: все SHA-256 совпали, прежние файлы не нужны.
Новый `server.py` отдельно загрузил встроенную CPU-модель без сети; доступ
к Docker из systemd user manager также проверен. Рабочий контейнер для этих
проверок не переустанавливался.
